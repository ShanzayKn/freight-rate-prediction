# Freight Rate Prediction — Machine Learning Engineering

A reproducible, batch-oriented machine learning project for predicting US freight shipment rates. Developed for the **Spotter Freight Rate Prediction Challenge** and presented as a portfolio example of exploratory analysis, data-quality handling, chronological validation, gradient boosting, experiment tracking, and submission validation.

## Problem and outputs

Given a shipment's pickup and delivery locations, distance, equipment, weight, and date, predict the **posted freight rate in USD**. The historical dataset includes **48,000 labeled shipments** (January–October 2025). The assessment provides **12,000 unlabeled shipments** to price, plus **31 fixed-route December 2025 scenarios** (Lexington → Fort Wayne, 360 miles, Dry Van, 32,000 lb; only the date changes).

Required deliverables:

- `validation_predictions.csv` with exactly `load_id,predicted_rate` for all 12,000 loads.
- Completed 31-row December prediction file and the chart generated by `score.py`.
- A PDF or DOCX report explaining validation, splitting, and results, including the December chart.
- This GitHub repository with dependencies and run instructions, and a 2–3 minute Loom walkthrough.

> **Evaluation scope:** The supplied `score.py` validates file structure and generates a chart. **Spotter's final hidden-set accuracy is unknown** until they evaluate the submission.

The submitted candidate uses **Basic CatBoost**, with pickup, delivery, distance, equipment, weight, and derived calendar features (`month`, `day_of_week`, `day_of_year`). This common feature set works for both assessment prediction schemas. The full-feature alternatives include `market_index`, `quote_signal`, and coordinates; they did not deliver consistent improvements in expanding-window backtesting.

### Data preparation

- Investigated **300 missing weights**, **374 missing market-index values**, and **292 negative weights** in the historical dataset.
- Treated negative weight signs as probable sign-recording errors and took absolute values, retaining a flag in the prepared dataset. This is a **documented assumption**, not verified source-data truth.
- Kept numerical missing weights as missing for CatBoost's native handling; the linear baseline instead imputes medians using training data.
- Did **not** automatically delete unusually high freight rates. A small group of very high dollars-per-mile shipments presents a significant modeling challenge.
- Excluded the target `posted_rate` and identifier `load_id` from model features; avoided using target-derived rate-per-mile as an inference feature.
- Preserved the original December input, with generated December rates saved separately.

### Chronological evaluation

- **Development fit:** January–June 2025 (**28,806** rows).
- **Development validation:** July–August 2025 (**9,671** rows).
- **Previously inspected holdout:** September–October 2025 (**9,523** rows); the January–August fit used **38,477** rows.
- **Expanding-window backtests:** trained through the preceding month and evaluated April, May, June, July, and August separately (**24,186** non-overlapping evaluated rows in total).
- **Final inference model:** refitted to all **48,000** labeled historical shipments before predicting the future unlabeled dataset.

The September–October holdout was inspected during development, so it is **not a pristine independent final test set**. Scores below are not the final assessment results.

## Results

### Expanding-window backtest (April–August 2025)

| Feature set | Pooled MAE (USD) | Pooled RMSE (USD) |
|---|---:|---:|
| **Basic** | **167.12** | **641.64** |
| Market | 177.36 | 644.10 |
| Full | 202.01 | 653.94 |

The pooled MAE weights monthly MAE by validation-row count. Pooled RMSE combines monthly mean-squared errors before taking the square root. These results motivated selecting **Basic** as the final candidate rather than relying on one favorable feature-comparison split.

### Earlier September–October holdout (Basic CatBoost)

| Metric | Result |
|---|---:|
| MAE | **$135.59** |
| RMSE | $639.02 |
| MAPE | 6.32% |
| WAPE | 5.67% |
| R² | 0.8247 |
| Median absolute percentage error | 3.05% |
| Within ±10% of actual rate | 93.46% |
| Within ±20% of actual rate | 98.10% |

**Interpretation:** “93.46% within ±10%” is a tolerance-based holdout statistic, **not** classification accuracy and **not** the hidden-set score.

### Error analysis and limitations

In the September–October holdout, just **73 of 9,523** shipments with observed freight rates above **$4/mile** contributed **90.59% of squared error**. That group can only be identified using actual prices *after the fact* and is **not available as an input label during inference**. This highlights the risk of rare exceptional prices and the importance of examining both MAE and RMSE.

Other limitations: the high-rate mechanism is not established; training and validation periods have differing pricing patterns; tree-based date features do not ensure reliable forecasting extrapolation; and additional `market_index`/`quote_signal` feature provenance has not been independently verified for live production use. The December chart is a **scenario prediction**, not evidence of realized December price accuracy.

## Technology decisions

| Tool | Role | Reason for selection / trade-off |
|---|---|---|
| Python 3.12 | Runtime | Broad ecosystem support; other compatible versions may work |
| Pandas + NumPy | Data and calculations | Good fit for a 48k-row tabular dataset; Polars/DuckDB may help at much larger scale |
| Scikit-learn | Baselines, preprocessing, metrics | Reliable standard ML interfaces |
| CatBoost (CPU) | Gradient-boosted tabular regressor | Native categorical support and nonlinear modeling; XGBoost/LightGBM are viable alternatives |
| Matplotlib | December chart | Used by the official scorer |
| pytest | Unit tests | Simple tests for feature transformations; not a substitute for statistical model validation |
| JSON records | Experiment tracking | Minimal and inspectable; MLflow could be added for team-scale tracking |

No API, database, or container is necessary for this **batch CSV submission**. Those would be separate extensions if an online inference use case emerges.

## Setup — Windows / VS Code / PowerShell

Prerequisites: Python 3.12 (tested with 3.12.6), VS Code, and the Python extension. From the repository root:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pytest -q
```

If PowerShell prevents activation, use `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` in that terminal or execute `.venv\Scripts\python.exe` directly.

The assessment's initial requirements specify:

```text
matplotlib>=3.8,<4
numpy>=1.26,<3
pandas>=2.0,<3
```

**Also required for this solution:** `scikit-learn>=1.5,<2`, `catboost>=1.2,<2`, and `pytest>=8,<10`. Ensure these lines are present in your local `requirements.txt`. Ranges allow different future versions; pinning resolved versions / a lockfile is recommended for stronger reproducibility.

### Place the input files

Copy the supplied assessment files under `data/raw/` using these exact normalized names:

```text
data/raw/train_test.csv
data/raw/validation.csv
data/raw/validation_predictions_template.csv
data/raw/december_chart_inputs.csv
```

The original package may use hyphens rather than underscores in some filenames. Keep `score.py` in the project root. If the provided template isn't available, it can be recreated from the 12,000 validation `load_id` values with an empty `predicted_rate` column; ensure IDs are unique. Never fabricate actual labels for the validation data.

### Reproduce the analysis and predictions

Run these commands from the project root:

```powershell
python src/prepare_data.py
python src/train_baseline.py
python src/compare_features.py
python src/backtest.py
python src/summarize_backtests.py
python src/train_catboost.py
python src/evaluate_final.py
python src/final_predict.py
python score.py --predictions validation_predictions.csv --december-predictions data/processed/december_predictions.csv
```

`src/evaluate_final.py` evaluates the earlier saved September–October holdout predictions, **not** Spotter's hidden answers. `src/final_predict.py` must be configured to **write** December predictions to `data/processed/december_predictions.csv` and must not overwrite the raw file. The official scorer validates both prediction files and creates `scorer_results/candidate_december.png`.

To quickly rerun only the submission after installing dependencies and placing data, use the final two commands above. Model training may take about a minute on a local CPU, depending on hardware.

## Portfolio discussion points

1. **Why chronological validation?** Predicting future shipments with information from future periods would make a historical evaluation unrealistic.
2. **Why CatBoost over Ridge?** Boosted trees model nonlinear tabular interactions; measured results support the choice, but it must be compared on identical folds to isolate algorithm effects.
3. **Why Basic over Full?** The richer feature set won one development split, but Basic achieved lower pooled error across five expanding-window backtests and can serve both submission input schemas.
4. **Why not remove expensive outliers?** They might be real business events. Removing them merely because they are hard to predict may make the system worse for important cases.
5. **What would improve production readiness?** Dataset and artifact checksums, clean dependency locks, explicit data contracts, integration tests, continuous monitoring, and a defined retraining policy.
